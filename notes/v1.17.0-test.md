# v1.17.0 build and KCM test

## Images built

All eleven components with public sources build from `src/` with nothing but
docker -- no Go toolchain, no upstream Makefile. Upstream's Dockerfiles pin
`golang:1.27.3` as the builder and `gcr.io/distroless/static:nonroot` as the
base, so a build is reproducible from this repo alone.

| image | size |
| --- | --- |
| addon-controller | 231 MB |
| classifier | 150 MB |
| healthcheck-manager | 143 MB |
| sveltoscluster-manager | 143 MB |
| event-manager | 141 MB |
| access-manager | 138 MB |
| shard-controller | 125 MB |
| clusterinventory-controller | 120 MB |
| sveltosctl | 110 MB |
| crd-manager | 74 MB |
| register-mgmt-cluster | 70 MB |

All eleven are published by `.github/workflows/images.yml` to
`ghcr.io/josef-hak/projectsveltos/<name>:v1.17.0` and are anonymously
pullable -- a cluster needs no imagePullSecret for them.

## KCM test, from the fork branch

`josef-hak/kcm@sveltos-images-ghcr` (one commit on top of `k0rdent/kcm@main`)
carries the registry override as the chart's own
`templates/provider/projectsveltos/values.yaml`, so a KCM built from it uses
these images with no Management config at all.

ksm-tests, `KCM_MODE=source`, `SRC_URL=https://github.com/josef-hak/kcm.git`,
ref `sveltos-images-ghcr`, and deliberately `SVELTOS_VALUES=` (empty) with
nothing preloaded into the node: the branch has to do all the work and every
image has to come over the network.

Up in 7m35s, `Management/kcm` Ready. Seven of the ten workloads pulled from
GHCR, the other three being the ones with no sources:

## KCM test, via Management config

ksm-tests, default variant (KCM 1.14.0-dev.1-5-gba9d29cb from
`oci://ghcr.io/k0rdent/kcm/staging`, which installs projectsveltos chart

`SVELTOS_SCALE_ZERO=""` so no component is scaled away, and
`SVELTOS_VALUES=kcm/values-ghcr.yaml`.

### Pulling from GHCR, not just from the preload

The run started from images preloaded into the node (`kcm/preload.sh`), so
to prove the registry itself works, addon-controller's image was deleted from
the node's containerd and its pod restarted. The kubelet pulled
`ghcr.io/josef-hak/projectsveltos/addon-controller:v1.17.0` in 5.3s with no
pull secret and the pod came back Ready.

### clusterinventory-controller

Not covered by the run above: the chart has it off by default and KCM does not
turn it on. Enabling it starts our image, which runs, reaches the API server
and then exits on a prerequisite KCM does not install:

```
unable to create controller  err="indexing ClusterProfile source secrets:
  unable to retrieve the complete list of server APIs:
  multicluster.x-k8s.io/v1alpha1: no matches for
  multicluster.x-k8s.io/v1alpha1, Resource=" controller="ClusterProfile"
```

That is the Cluster Inventory API CRD missing, not a fault in the build --
the upstream image behaves the same way. The flag was turned back off and the
Management returned to `Ready=True`.

### sveltosctl

Not part of the chart, so it has no place in a KCM run. Smoke-tested on its
own: `sveltosctl version` reports `v1.17.0` and commit `3d45623...`. Upstream's
own published image reports neither -- its buildx target passes no LDFLAGS --
so `scripts/build.sh` supplies them from `src/sveltosctl/SOURCE`.
