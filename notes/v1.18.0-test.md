# v1.18.0 build and KCM test

## What changed from v1.17.0

All eleven repositories with public sources tag `v1.18.0`; the five without
one -- sveltos-agent, drift-detection-manager, techsupport, mcp-server,
sveltos-applier -- are still 404.

Upstream's Dockerfiles changed in two ways that matter here:

- a `GIT_COMMIT` build arg now feeds `org.opencontainers.image.revision`,
  which `scripts/build.sh` supplies from `src/<dir>/SOURCE`;
- the build is now `COPY . .` with `.git` included and `go build ./cmd`
  instead of `cmd/main.go`, so the Go toolchain stamps the module version into
  the binary. A vendored tree has no `.git` and cannot have one -- git would
  treat `src/<dir>` as a submodule -- so `go version -m` on our binaries
  reports `(devel)` where upstream's reports the tag. Nothing reads it at
  runtime; it surfaces in image scanners. The version and the upstream commit
  are on the image as OCI labels either way.

The chart's own image keys are unchanged between 1.17.0 and 1.18.0, so
`kcm/values-ghcr.yaml` carried over untouched.

## The closed-source surface is now almost nil

`k0rdent/kcm@main` moved to projectsveltos chart 1.18.0 in #3222, which also
disables the optional components -- including `agent.enabled: false`, a flag
chart 1.18.0 adds. That one takes away sveltos-agent and, with it,
event-manager and hc-manager, which the chart only deploys alongside the
agent.

With those values plus the registry override, every image the chart renders is
one we build:

```
Deployment addon-controller       ghcr.io/josef-hak/.../addon-controller:v1.18.0
Deployment classifier-manager     ghcr.io/josef-hak/.../classifier:v1.18.0
Deployment sc-manager             ghcr.io/josef-hak/.../sveltoscluster-manager:v1.18.0
Job        crd-manager-job        ghcr.io/josef-hak/.../crd-manager:v1.18.0
Job        register-mgmt-cluster  ghcr.io/josef-hak/.../register-mgmt-cluster:v1.18.0
```

`drift-detection-manager` is the only closed image left in reach, and only at
run time: addon-controller places it in a managed cluster for a ClusterProfile
in `ContinuousWithDriftDetection` mode, from a reference built out of
`--registry`, which is why that is left at docker.io.

## KCM test

ksm-tests, `KCM_MODE=source`, `SRC_URL=https://github.com/josef-hak/kcm.git`,
ref `sveltos-images-ghcr` (commit `d7bc9d0b` on `k0rdent/kcm@main`
`21ea2ded`), `SVELTOS_VALUES=` empty and nothing preloaded, so the branch does
all the work and every image comes over the network.

Up in 7m0s, `Management/kcm` Ready, all three Deployments Ready on our images.
Grepping every pod in the cluster for a sveltos image returns ours and
nothing else.
